# Аналітичний звіт: Оптимізація запиту в БД 'plants'

**Мета:** Проаналізувати та оптимізувати "повільний" SELECT-запит за допомогою індексування.

**Об'єкт аналізу:** Таблиця `Order`.

## 1. Цільовий "повільний" запит

Ми будемо діагностувати запит, який шукає всі замовлення з певним статусом. У реальній системі такий запит виконується часто (наприклад, "показати всі замовлення в обробці") і може бути повільним, оскільки таблиця `Order` постійно зростає.

План виконання "ДО" (Без індексу)
SELECT * FROM `Order` WHERE `status` = 'Pending';
EXPLAIN SELECT * FROM `Order` WHERE `status` = 'Pending';

Результат "ДО":
+---+------------+--------+-------+--------------+------+--------+------+-------+------+
|id |select_type |`table` |`type` |possible_keys |`key` |key_len |`ref` |`rows` |Extra |
+---+------------+--------+-------+--------------+------+--------+------+-------+------+
| 1 |SIMPLE      |Order   |ALL    |[NULL]        |[NULL]|[NULL]  |[NULL]|12     |[NULL]|
+---+------------+--------+-------+--------------+------+--------+------+-------+------+
type: ALL: Це найгірший показник. Він означає Full Table Scan (Повний перебір таблиці). 
База даних змушена послідовно прочитати кожен рядок у таблиці Order (12 рядків),
щоб порівняти, чи дорівнює status значенню 'Pending'.
possible_keys: NULL: MySQL не бачить жодних індексів, які б могли допомогти цьому запиту.
key: NULL: Оскільки немає можливих індексів, жоден індекс і не використовується.
Extra: Using where: Це означає, що фільтрація відбувається "на льоту" під час сканування.
CREATE INDEX idx_order_status ON `Order` (status);

Створення індексу
CREATE INDEX idx_order_status ON `Order` (status);

План виконання "ПІСЛЯ" (З індексом)
EXPLAIN SELECT * FROM `Order` WHERE `status` = 'Pending';

Результат "ПІСЛЯ":
+---+------------+--------+-------+----------------+----------------+--------+------+-------+---------------------+
|id |select_type |`table` |`type` |possible_keys   |`key`           |key_len |`ref` |`rows` |Extra                |
+---+------------+--------+-------+----------------+----------------+--------+------+-------+---------------------+
| 1 |SIMPLE      |Order   |ref    |idx_order_status|idx_order_status|514     |const | 2     |Using index condition|
+---+------------+--------+-------+----------------+----------------+--------+------+-------+---------------------+

type: ref: Кардинальна зміна! Замість ALL (сканування всієї таблиці), оптимізатор використовує тип ref. 
Це означає, що він використовує індекс для прямого пошуку (lookup) всіх рядків, де key (idx_order_status) дорівнює константі ('Pending').
possible_keys: idx_order_status: MySQL побачив, що наш новий індекс може бути використаний.
key: idx_order_status: Оптимізатор вирішив використати наш індекс, оскільки це найефективніший спосіб.
rows: 2: Зверніть увагу на різке зменшення рядків. Замість сканування всієї таблиці (12 рядків), 
MySQL тепер прогнозує, що йому потрібно прочитати лише 2 рядків, які безпосередньо відповідають умові.
